# Закрытый демонстрационный стенд на Yandex Compute Cloud

Поставка предназначена для одного стенда с синтетическими данными. Пользователь подключается по SSH и открывает HTTPS-адрес через туннель. Пароль Nginx ограничивает доступ ко всему стенду. В приложении отсутствуют этап 4.6, учётные записи и права на проекты, персонал, табели и начисления. Любой допущенный к стенду оператор видит все объекты и может выполнять доступные операции. Публичная многопользовательская эксплуатация заблокирована до реализации и проверки модели доступа.

## Состав

```text
Браузер → SSH-туннель → 127.0.0.1:8443 на ВМ
       → Nginx, TLS + пароль стенда
       → Unix-сокет 0600 → Waitress (один процесс, четыре потока)
       → Flask → SQLite на постоянном блочном диске
```

Программный образ содержит Python 3.13.12, закреплённые Linux-совместимые пакеты Flask и Waitress, модули, шаблоны, статику и миграции. В облачном профиле приложение получает только Unix-сокет, его сетевой режим — `none`. Прокси сохраняет исходный Host, удаляет `Authorization`, `Forwarded` и `X-Forwarded-*` для доверенных приложением полей. HTTPS-схему задаёт WSGI. Сервер получает peer `localhost` непосредственно от Waitress для Unix-сокета, точный Origin и CSRF-токен проверяет Flask. Смена объекта в другой вкладке не разрешает запись из устаревшей формы. Cookie `__Host-plankton-v2` имеет Secure, HttpOnly, Path=/ и SameSite=Strict. Секрет сессии сохраняется вне образа. Остановка через веб-маршрут отключена.

Оба контейнера выполняются с непривилегированным UID/GID, с файловой системой образа только для чтения, без Linux capabilities. Временные файлы удаляются при пересоздании. Проксирование ограничено WSGI, служебные каталоги не выставлены в веб. Предел тела HTTP на прокси — 5 МиБ + 64 КиБ. Flask ограничивает обычную форму 128 КиБ, отдельные формы импорта допускают файл до 5 МиБ. Экспорты XLSX передаются браузеру, постоянный серверный каталог экспорта этой версии не нужен.

## 1. Виртуальная машина и сеть

1. В существующем каталоге Yandex Cloud выберите Compute Cloud → Создать ВМ. Для первой проверки подойдёт отдельная ВМ Ubuntu 24.04 LTS x86_64. Начальная конфигурация для небольшого стенда — 2 vCPU и 4 ГиБ ОЗУ. Это ориентир для проверки, нагрузочная ёмкость на Yandex Cloud не измерялась. На действующей ВМ используйте отдельный каталог программы, постоянное пространство данных, порт и имя Compose-проекта. Существующую установку не переключайте. [ВМ Linux](https://yandex.cloud/ru/docs/compute/operations/vm-create/create-linux-vm)
2. Выберите приватную подсеть, вход по SSH-ключу, подключение через доступный администратору VPN или bastion. Назначьте выделенную группу безопасности. Разрешите входящий TCP 22 только от административного CIDR или bastion. Порты 80, 443, 8443 и WSGI не добавляйте во входящие правила. Для установки пакетов и образов нужен исходящий доступ, либо используйте поставку предварительно собранных образов. [Группы безопасности](https://yandex.cloud/ru/docs/vpc/operations/security-group-create) · [SSH](https://yandex.cloud/ru/docs/compute/operations/vm-connect/ssh)
3. При выборе существующего каталога на постоянном диске проверьте `findmnt --target /srv` и `df -h /srv`. Для отдельного диска создайте блочный диск в зоне ВМ, присоедините его в разделе дисков и сопоставьте идентификатор с `lsblk -f`. Создание раздела и форматирование допустимы только для нового пустого диска. Установите точку монтирования, например `/srv/plankton-v2`, занесите UUID раздела ext4 в `/etc/fstab` и проверьте результат `findmnt --target /srv/plankton-v2`. Проверьте автоподключение после перезапуска ВМ до запуска Compose. Для существующего раздела используйте его файловую систему. Контейнеры получают bind mounts с `create_host_path: false`, отсутствие подготовленного каталога прерывает старт. [Подключение блочного диска](https://yandex.cloud/ru/docs/compute/operations/vm-control/vm-attach-disk)
4. База, WAL, файлы восстановления и копии требуют места с запасом. Для миграции оставьте место для живой БД, снимка, возможной дополнительной копии мигратора и временной работы SQLite. Сетевые файловые системы NFS/SMB и параллельные реплики приложения для этого профиля не поддерживаются. Экземпляр удерживает эксклюзивную блокировку на каталог базы.

## 2. Docker и ручная доставка

Для чистой Ubuntu подключите официальный APT-репозиторий Docker по инструкции производителя. Затем установите движок, плагины и инструменты для проверки HTTPS.

```sh
sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin openssl curl
docker version
docker compose version
```

Требуются Docker Engine 28+ и Compose 2.20.2+. В Docker до 28 публикация на localhost допускала доступ с того же L2-сегмента. Пользователь, запускающий команды Docker, получает административные возможности демона. Используйте отдельного доверенного оператора, проверьте принадлежность смонтированных каталогов, особенно при работе с rootless Docker. [Установка Docker](https://docs.docker.com/engine/install/ubuntu/) · [Привязка портов к localhost](https://docs.docker.com/engine/network/port-publishing/)

Передайте архив по SCP на новую ВМ или посредством существующего защищённого канала. Пример использует уже настроенный SSH-псевдоним `demo-vm` и помещает исходники в отдельный каталог релиза.

```sh
scp plankton-time-cloud.tar.gz demo-vm:~/
ssh demo-vm
mkdir -p ~/releases/v2
tar -xzf ~/plankton-time-cloud.tar.gz -C ~/releases/v2
cd ~/releases/v2/plankton-time-cloud
cp .env.example .env
chmod 600 .env
```

Сверьте SHA-256 с переданным отдельно значением перед распаковкой. Файл `.env` читают Compose и Bash. Записывать его должен только доверенный оператор. Для значений с пробелами используйте одинарные кавычки.

## 3. Параметры и первый пуск

| Параметр | Назначение |
|---|---|
| `COMPOSE_PROJECT_NAME` | Отдельное имя сервиса для всех версий одного стенда. Для другого стенда задайте новое имя. |
| `STATE_DIR` | Абсолютный путь на постоянном диске. Здесь создаются `plankton.sqlite3`, WAL/SHM, `.serve.lock` и `backups/`. |
| `CONFIG_DIR` | Отдельный абсолютный каталог. Здесь находится ключ сессии, ключ TLS, хеш пароля прокси и файл входа оператора `client.netrc`. |
| `DEMO_HOST` | Внешнее имя, по умолчанию `127.0.0.1`. Для частного домена задайте DNS-имя до выпуска сертификата. |
| `DEMO_PORT` | Свободный порт 1024–65535 на loopback. Для SSH-туннеля и браузера используйте то же число. |
| `DEMO_UID`, `DEMO_GID` | Ненулевые идентификаторы владельца файлов, обычно `id -u` и `id -g`. Оба контейнера должны иметь доступ к Unix-сокету 0600. |
| `APP_IMAGE`, `PROXY_IMAGE` | Тег своего релиза и закреплённый digest Nginx. Новому релизу присваивайте отдельный тег приложения. |
| `PLANKTON_ENV` | Необязательный внешний путь к файлу параметров для `ops.sh`. По умолчанию берётся `.env` текущего релиза. |
| `BUILD_CA_FILE` | Необязательный доверенный набор CA для HTTPS при сборке через корпоративный прокси. Передаётся через временный BuildKit secret. |

Подготовьте **родительский** каталог на постоянном диске, принадлежащий оператору. Например, после проверки точки монтирования на новой ВМ можно установить владельца именно нового каталога командой `sudo chown "$(id -u):$(id -g)" /srv/plankton-v2`. Убедитесь, что он недоступен посторонним. Укажите в `.env` два отдельных дочерних пути. Утилита `init` создаёт новый каталог доступа, а при существующем останавливается, чтобы не заменить ключи.

```sh
./deploy/scripts/ops.sh init
./deploy/scripts/ops.sh build
./deploy/scripts/ops.sh start
./deploy/scripts/ops.sh health
docker compose ps
```

Сборка получает публичный Python-образ по digest и зафиксированные колёса PyPI. Скрипт получает публичный образ Nginx по digest, если его ещё нет на машине. Запуск использует только имеющиеся образы. На первом старте приложение создаёт новую базу, применяет миграции и заполняет начальные справочники. Персональные данные для этого не нужны. Проверка `/healthz` проходит через TLS и реальный пароль, обращается к SQLite и выдаёт `ok`. Облачный профиль выставляет WAL. Запуск новой версии на совместимой старой схеме сначала сохраняет проверенный снимок. Неизвестные версии схемы и нарушение целостности останавливают загрузку.

**Вариант без доступа ВМ к реестрам.** На доверенной Linux-машине той же архитектуры выполните `ops.sh build`, присвойте уже проверенному digest Nginx явный локальный тег и сохраните оба образа. Значения `$PROXY_IMAGE` и `$APP_IMAGE` находятся в подготовленном файле `.env`.

```sh
. ./.env
docker tag "$PROXY_IMAGE" plankton-private-proxy:1.30.7
docker image save -o plankton-images.tar "$APP_IMAGE" plankton-private-proxy:1.30.7
sha256sum plankton-images.tar
```

Передайте архив образов и исходную поставку, проверьте контрольную сумму на ВМ и выполните `docker image load -i plankton-images.tar`. Укажите `PROXY_IMAGE=plankton-private-proxy:1.30.7` и перенесённый тег `APP_IMAGE` в `.env` новой ВМ. Выполните `init`, затем `start`. GitHub и собственный Container Registry для обоих вариантов доставки не требуются.

## 4. Браузер, сертификат и контроль доступа

`init` создаёт отдельный локальный CA, серверный сертификат на 180 дней с SAN для заданного хоста, случайный пароль Nginx для имени `demo` и ключ подписания сессии. Секретный ключ CA после выдачи сертификата удаляется. Ключи, хеш пароля и `client.netrc` хранятся с режимом 0600 под каталогом 0700. Открывайте этот файл только в доверенной сессии оператора. Не пересылайте пароль или ключи вместе с исходным архивом. CA сертификат `ca.crt` публичный, его SHA-256 проверьте по отдельному доверенному каналу перед импортом в профиль браузера. Для продления замените сертификат и ключ от доверенного внутреннего CA, настройте файл `ca.crt` для проверки и пересоздайте прокси. Не отключайте проверку TLS в браузере.

Туннель запускается на **компьютере оператора**. Оставьте SSH-сеанс активным до конца работы с браузером.

```sh
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8443:127.0.0.1:8443 demo-vm
```

Перейдите на `https://127.0.0.1:8443/` и введите имя и пароль закрытого стенда. Для частного домена настройте его разрешение на `127.0.0.1` на компьютере оператора. Браузер, сертификат и `DEMO_HOST` должны использовать одно имя. Внешний адрес или публичный DNS для приложения не требуются. При проверке с ВМ запрос без пароля должен получить код 401.

```sh
. ./.env
curl --noproxy '*' --resolve "$DEMO_HOST:$DEMO_PORT:127.0.0.1" --cacert "$CONFIG_DIR/ca.crt" \
     -o /dev/null -w '%{http_code}\n' "https://$DEMO_HOST:$DEMO_PORT/healthz"
```

Создайте синтетический объект с узнаваемым кодом, выполните `ops.sh stop` и `ops.sh start`, проверьте код в разделе объектов. Для проверки пересоздания используйте процедуру обновления ниже. Остановку начинают с прокси, чтобы завершить текущие HTTP-запросы, затем останавливают Waitress.

## 5. Резервирование и восстановление

```sh
./deploy/scripts/ops.sh backup
```

Команда печатает имя нового файла в `$STATE_DIR/backups/`. Согласованный снимок читается через SQLite Backup API, включая зафиксированные записи в WAL. Проверяются `integrity_check`, `foreign_key_check`, таблицы и версия схемы. Только полностью записанный и проверенный снимок публикуется под уникальным именем. Закрытая копия автономна и не требует файлов WAL/SHM. Действующий файл открытой базы не копируйте через `cp` или `scp`.

Политика поставки сохраняет все версии без автоматической очистки. Оператор проверяет свободное место и переносит проверенные копии в отдельное защищённое хранилище. Копии на одном диске с БД защищают от ошибки обновления, при утрате самого диска понадобится внешняя копия. График для стенда можно привязать к началу каждой испытательной сессии и каждому обновлению. Периодически выполняйте пробное восстановление. Храните конфигурацию и ключи отдельно в защищённом хранилище, на производство персональные данные из стенда не переносите.

Восстановление выполняется в **новый каталог** рядом с текущей базой. Родительский каталог должен существовать и быть доступен UID приложения. Подставьте имя, которое вывела команда резервирования.

```sh
./deploy/scripts/ops.sh restore /srv/plankton-v2/data/backups/plankton-ЗАМЕНИТЬ.sqlite3 \
    /srv/plankton-v2/recovered-001
```

Утилита проверяет содержимое ещё раз и создаёт `recovered-001/plankton.sqlite3`. Попытка повторно использовать каталог завершится отказом. Для испытания выбранной копии остановите изолированный стенд, укажите `STATE_DIR=/srv/plankton-v2/recovered-001` в его `.env`, запустите `start`, `health` и проверьте данные через браузер. Оригинальная база остаётся по прежнему пути. Для параллельного сравнения подготовьте для второго стенда собственные имя Compose, конфигурацию, порт и восстановленную базу. Совместимую копию из другой установки сначала проверяйте в отдельном пространстве и только с разрешёнными данными.

## 6. Обновление и откат

1. Сохраните предыдущий каталог программы, `.env`, старые теги/ID образов. Проверьте, что действующая схема открывается старым образом и оператор имеет место под новую проверенную копию. Распакуйте релиз в другой каталог. Перенесите параметры стенда, сохраняя имя Compose, порт, `STATE_DIR` и `CONFIG_DIR`. Назначьте новый уникальный тег `APP_IMAGE`.
2. Соберите новый образ командой `./deploy/scripts/ops.sh build` в новом каталоге, либо загрузите заранее подготовленные образы. До завершения операции обслуживает предыдущий контейнер.
3. Запустите `./deploy/scripts/ops.sh update` из нового каталога. Прокси заканчивает обслуживание входящих запросов. Утилита в старом работающем контейнере делает проверенный снимок, печатает его имя и останавливает старый сервер. Compose пересоздаёт контейнеры, новая версия запускает необходимые миграции и проходит проверку по HTTPS. При ошибке копирования или старта скрипт возвращает ненулевой код. До выяснения причины оставьте вход закрытым. Для повторной попытки после неудачной миграции сначала проверьте журнал, копию и выбранный каталог.
4. Проверьте `health`, наличие ранее созданного объекта и нужные операции. Перед следующим обновлением запишите версию и имя подходящей копии. Для отката остановите экземпляр командой `ops.sh stop`, восстановите **копию до обновления** в пустой каталог. В `.env` старого релиза укажите старые образ и восстановленный путь, прежний `CONFIG_DIR` и то же имя Compose. Запустите из старого релиза `ops.sh start`, `ops.sh health` и сверьте данные. Откат на копию возвращает записи к моменту снимка, новые записи после этого момента требуют отдельной сверки. Понижение версии поверх изменённой базы не предусмотрено.

## 7. Диагностика и приёмка

```sh
docker compose ps -a
docker compose logs --tail 100 app proxy
./deploy/scripts/ops.sh health
df -h /srv/plankton-v2
```

Подставьте `docker compose --env-file /путь/к/файлу`, если настройки лежат отдельно. Журналы стандартных потоков контейнеров ротируются драйвером Docker, 3 файла по 5 МБ на сервис. Nginx не ведёт журнал строк запросов, ошибки идут в stderr. Журнал бизнес-операций приложения находится в базе и попадает в резервные копии. При 401 проверьте файл входа и хеш прокси. При 403 проверьте точный адрес в браузере, актуальность сессии, объект в другой вкладке и корректность Origin. При 502 проверьте состояние WSGI, режимы 0700/0600 у сокета, UID и свободное место. При проблемах с миграцией проверьте версию, целостность и наличие допусков к каталогу. Не удаляйте WAL/SHM работающей базы.

Сквозной тест создаёт временные собственные файлы доступа, БД, образы с отдельным тегом и случайный loopback-порт. Для запуска нужны Bash, Docker и Python 3.10+. Выполняйте проверку под непривилегированным пользователем тестовой машины.

```sh
mkdir -p /tmp/plankton-acceptance
python3 deploy/scripts/smoke.py --workspace /tmp/plankton-acceptance
```

Он проверяет HTTPS и изоляцию, формы и пределы загрузки, сохранение параллельных записей, согласованную копию при открытом WAL, версии и целостность, остановку и рестарт, смену image ID, повторное пересоздание, откат образа с открытием отдельно восстановленной БД и обновление синтетической схемы 012. При установленном Playwright добавьте `--chromium /usr/bin/chromium` для проверки пяти страниц в браузере и попыток внешних запросов. Результаты выпуска приведены в итоговом отчёте. Сведения о ВМ, SSH, дисках и безопасности сверены 20 ноября 2026 года по официальной документации. Реальная ВМ Yandex Cloud для этих проверок не создавалась.
